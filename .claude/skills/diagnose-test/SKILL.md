# diagnose-test

판단 근거는 `docs/issues/test-refactor/methodology.md` 의 `[M1]`~`[M9]` 다. 시작 전에 반드시 읽는다.
대상(args)은 디렉토리 또는 파일 목록이다. 테스트 파일과 함께 그 대상 소스 파일도 읽는다.

## 판단 기준

`[M1]` 4요소(회귀 방지, 리팩터링 내성, 빠른 피드백, 유지보수성). 하나라도 0이면 가치 0.

## 테스트마다 확인할 것

- 구현 결합 `[M2]`: 내부 함수 호출, 호출 순서, 내부 state 를 단언하는가?
- Mock 과다 `[M3]`: 내부 모듈이나 우리 DB 를 mock 하는가? stub 값을 그대로 돌려받는지만 확인하는가?
- 레이어 오배치 `[M4]`: C 분류 코드를 테스트하는가? A 분류 로직이 E2E 로만 검증되는가? 중복 검증이 있는가?
- 케이스 누락 `[M5]`: A 분류인데 경계값/결정 테이블 관점에서 빠진 케이스가 있는가?
- 가독성 `[M6]`: 셋업이 의도를 가리는가? 테스트 안에 로직이 있는가? 이름이 동작을 설명하는가?
- 결정성 `[M7]`: 시간/랜덤/순서/공유 상태/고정 대기 의존이 있는가?
- 헛검증 `[M8]`: 단언이 없거나 항상 참인가? 대상 코드를 깨뜨려도 통과할 구조인가?
- E2E `[M9]`: POM 누수, 비 web-first 단언, scenario.md Then 미검증, reload 없는 영속성 단언.

다른 작업과 작업 트리를 공유하는 경우 파일을 수정하지 않는다. 헛검증 의심은 "의심" 으로만 표기한다.

## 출력

1. 표: `| 파일 | 테스트(또는 describe) | ① | ② | ③ | ④ | 문제 | 근거 태그 | 처분 |`
   - 평가는 O / △ / X. 처분은 유지 / 재작성 / 레이어 이동 / 삭제.
   - 삭제는 그 동작이 다른 곳에서 이미 검증되는지 함께 적는다.
2. 반복 패턴 상위 3개와 우선순위 제안.
3. 테스트가 없는데 A 분류인 소스 (커버 공백).
