# 테스트 작성 방법론

테스트를 작성하거나 진단할 때의 판단 근거다. 규칙은 이 방법론에서 파생되며, 규칙에 없는 상황은 여기로 돌아와 판단한다.
각 절의 태그(`[M1]` 등)는 스킬(`.claude/skills/write-test`, `.claude/skills/diagnose-test`)과 리뷰 코멘트에서 근거를 가리킬 때 쓴다.

## [M1] 좋은 테스트의 4요소

출처: Vladimir Khorikov, _Unit Testing: Principles, Practices, and Patterns_ 4장

테스트 가치 = ① 회귀 방지 × ② 리팩터링 내성 × ③ 빠른 피드백 × ④ 유지보수성

| 속성            | 질문                                     | 깨지는 신호                                     |
| --------------- | ---------------------------------------- | ----------------------------------------------- |
| ① 회귀 방지     | 실제 버그가 생기면 실패하는가?           | mock 이 많아 실제 코드를 거의 실행하지 않음     |
| ② 리팩터링 내성 | 동작은 같고 내부만 바꿨을 때 통과하는가? | 함수명·호출 순서만 바꿔도 깨짐 (false positive) |
| ③ 빠른 피드백   | 충분히 빨리 도는가?                      | 느려서 로컬에서 안 돌림                         |
| ④ 유지보수성    | 읽고 고치기 쉬운가?                      | 셋업이 본문보다 길고 의도가 안 읽힘             |

- 곱이므로 하나라도 0이면 가치도 0이다.
- ②④는 사실상 이진값이라 반드시 확보한다. ①과 ③은 상충하므로 레이어마다 균형을 고른다 (E2E 는 ① 높고 ③ 낮음, 유닛은 반대).
- 가장 해로운 테스트는 리팩터링에 깨지는 테스트다. 쌓이면 팀이 빨간불을 무시하고, 스위트 전체가 신뢰를 잃는다.

## [M2] 동작을 테스트한다, 구현이 아니라

출처: Kent C. Dodds / Testing Library Guiding Principles, _Software Engineering at Google_ 12장

> 테스트가 소프트웨어가 사용되는 방식과 닮을수록 더 큰 신뢰를 준다.

- 관찰 가능한 동작만 단언한다. 우선순위:
  1. output-based: 입력 → 반환값 (가장 견고)
  2. state-based: 공개된 상태 변화
  3. communication-based: 시스템 경계 밖으로 나가는 호출 (가장 취약, 최소화)
- 구현 세부사항: 내부 함수, 호출 순서, 내부 state, private 헬퍼, 컴포넌트 내부 구조. 단언 대상이 아니다.
- 판별 질문: "이 테스트가 깨졌을 때 호출자/사용자에게 실제 문제가 생겼는가?" 아니면 구현 결합이다.

## [M3] Test Double 계층

출처: _Software Engineering at Google_ 13장, Khorikov 5·8장

실제 객체 > Fake > Stub > Mock. 일을 해낼 수 있는 가장 약한 것을 쓴다.

| 의존성 종류      | 예시                                | 처리                                  |
| ---------------- | ----------------------------------- | ------------------------------------- |
| 내부 협력 객체   | 우리 저장소의 다른 모듈             | mock 하지 않는다. 실제를 쓴다         |
| managed 의존성   | 우리 앱만 쓰는 DB                   | mock 하지 않는다. 통합에서 실제/Fake  |
| unmanaged 의존성 | 외부 API, Sentry, 웹훅, 이메일, LLM | 이 호출만 mock 대상 (상호작용이 계약) |

- mock 은 "의존성이 이렇게 동작할 것"이라는 가정을 박아 넣는다. 가정이 틀려도 초록이라 ①이 사라지고, 호출 형태에 결합되니 ②도 사라진다.
- stub 은 입력 공급용이다. stub 호출 여부를 단언하지 않는다.
- stub 한 값이 그대로 반환되는지만 보는 테스트는 아무것도 검증하지 않는다 (tautology).

### 이 저장소에서의 해석

- `fetch` 는 브라우저→우리 API 경계다. 클라이언트 API 레이어(`entities/*/api`, `features/*/api`) 에서 `fetch` 를 stub 하는 것은 허용되지만, 단언은 "요청 형태(URL·메서드·body) + 응답 매핑·에러 처리" 처럼 그 모듈이 책임지는 동작이어야 한다. 단순 pass-through 래퍼는 [M4] C 분류로 본다.
- `packages/db` 쿼리는 managed 의존성이다. Drizzle 체인을 mock 해 "호출됐다"를 단언하는 대신 실제 DB(로컬/테스트 스키마) 통합 테스트가 원칙이다.

## [M4] 코드 분류와 레이어 배분

출처: Khorikov 7장, Kent C. Dodds Testing Trophy, Martin Fowler Test Pyramid

| 분류                       | 특징                     | 테스트                                                       |
| -------------------------- | ------------------------ | ------------------------------------------------------------ |
| A. 도메인 로직/알고리즘    | 복잡도 높음, 협력자 적음 | 유닛을 촘촘하게 (투자 대비 효과 최대)                        |
| B. 컨트롤러/오케스트레이션 | 복잡도 낮음, 협력자 많음 | 통합 소수 (행복 경로 + 유닛으로 못 잡는 엣지)                |
| C. 단순 코드               | 둘 다 낮음               | 테스트하지 않음                                              |
| D. 과복잡 코드             | 둘 다 높음               | 테스트 전에 A+B 로 분리 (Functional Core / Imperative Shell) |

- Testing Trophy: 정적 분석(타입/린트) → 유닛 → 통합(가장 두꺼움) → E2E(핵심 여정만).
- 같은 동작은 가장 낮은 레이어에서 한 번만 검증한다. 중복은 ③④만 깎는다.

## [M5] 테스트 케이스 설계 기법

출처: ISTQB Foundation Level 블랙박스 기법

동작 하나에서 어떤 케이스를 몇 개 만들지는 감이 아니라 이 기법으로 도출한다.

- 동등 분할: 같은 방식으로 처리되는 입력 집합마다 대표값 1개.
- 경계값 분석: 각 분할의 경계와 그 ±1. 예: 5회 락아웃 → 4회/5회/6회, 15분 → 14:59/15:00/15:01.
- 결정 테이블: 조건 2개 이상 조합 시 조합별 결과 표, 의미 있는 열마다 케이스 1개. 예: 권한 × 프로젝트 존재 × 입력 유효.
- 상태 전이: 상태가 있는 도메인(테스트 런, 마일스톤 등)은 상태/이벤트 표에서 유효 전이 전부 + 대표 무효 전이.
- 오류 추정: null/undefined, 빈 배열, 중복, 동시 요청, 타임존, 한글/이모지/긴 문자열, 네트워크 실패, 외부 응답 스키마 불일치(LLM·웹훅 응답 불신).

## [M6] 구조와 가독성

출처: AAA / Given-When-Then, _Software Engineering at Google_ 12장 (DAMP)

- Arrange / Act / Assert. Act 는 한 줄. 여러 줄이면 공개 API 캡슐화 문제 신호다.
- 테스트 하나 = 동작 하나 (단언 개수가 아니라 동작 단위).
- 테스트 안에 로직 금지. if/for/계산으로 기대값을 만들면 대상 코드의 버그를 그대로 복제한다. 기대값은 리터럴.
- DAMP > DRY. 테스트는 실행 가능한 명세다. 공통화는 의도를 숨기지 않는 팩토리/빌더까지만.
- 이름은 동작 명세. 한국어 평서문 + 마침표 (예: `비밀번호를 5회 틀리면 15분간 잠긴다.`). 함수명을 넣지 않는다.

## [M7] FIRST

Fast / Isolated / Repeatable / Self-validating / Timely

- 시간, 랜덤, ID, 실행 순서, 공유 상태, 네트워크는 flaky 의 원천이다. 통제하거나 주입한다 (`vi.useFakeTimers`, `vi.setSystemTime`).
- 사람이 결과를 해석해야 하는 테스트는 테스트가 아니다.

## [M8] 실패를 먼저 본다

출처: Kent Beck TDD (Red-Green), Mutation Testing

- 한 번도 실패하지 않은 테스트는 무엇을 검증하는지 증명되지 않았다.
- 작성 후 대상 분기를 일부러 깨뜨려 빨간불을 확인하고 원복한다 (수동 mutation).
- 핵심 도메인·보안 모듈은 필요 시 StrykerJS 로 mutation score 를 측정한다.

## [M9] E2E

출처: Playwright 공식 Best Practices, 이 저장소 `AGENTS.md` 테스트 절

- 사용자가 인지하는 방식으로 찾는다: role > label/text > test id > CSS. CSS 클래스를 지워도 UX 가 같다면 테스트도 깨지면 안 된다.
- web-first assertion 만 쓴다. 고정 대기(`waitForTimeout`)는 느리면서 flaky 하다.
- 테스트마다 자기 데이터와 상태를 소유한다. 병렬 워커에서 충돌하지 않는 고유 suffix.
- POM 에 로케이터와 단언 의도를 캡슐화한다. UI 구조가 바뀌면 POM 한 곳만 고친다.
- scenario.md(Given/When/Then)가 먼저다. 영속성 Then 은 reload 후 재단언한다.
- 핵심 사용자 여정만 E2E 로 둔다. 엣지 케이스는 아래 레이어로 내린다.

## 커버리지 정책

출처: Google Testing Blog "Code Coverage Best Practices" (2020), Martin Fowler "TestCoverage"

- 커버리지는 음성 지표다. 낮으면 문제 신호지만 높다고 품질을 보장하지 않는다. 실행 여부만 재고 검증 여부는 재지 않는다.
- 100% 는 목표로 삼지 않는다. 그 구간의 코드는 대부분 C 분류이고, 덮으려면 ②④를 깎는다.
- Google 기준 참고치: 60% 수용, 75% 칭찬할 만함, 90% 모범. 전사 단일 수치 강제는 지양하고 변경분(diff) 커버리지를 본다.
- 운영 방식: 모듈별 차등(A 분류 경로는 높게), branch 우선, 전역은 실측치 바닥의 ratchet, 핵심 모듈은 mutation score.
